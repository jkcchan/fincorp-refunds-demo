# Architecture, evidence, limitations

`fincorp.settings` selects one of two Django apps. Each app has its own auth/session/SQLite tables (`control.sqlite3`, `refunds.sqlite3`). The trusted `scripts/run_checkout.py` launcher gives even historical candidate commits distinct runtime and preview session cookie names on localhost; the controller already has its own cookie. Historical `capture.js` reads the default `csrftoken` cookie, so the launcher leaves that name unchanged on those commits. Logging into another historical instance can invalidate an already-open form; reload it before submitting. Later commits name both cookies themselves. Only the refunds runtime enqueues repairs from frontend/server telemetry; each preview writes its errors to its own DB, which the worker attaches to that run without spawning a repair. Console packets include the local Git base, sanitized captured stack/log, synthetic reproduction, setup and acceptance. Persisted `Change`, `Job`, `Event`, `Review`, and `Incident` rows are the source of truth. Provider status/messages are facts about the session, **not** proof of code/test/release.

The one worker scans new errors, polls all associated live sessions, and processes bounded persisted jobs. Each candidate runs its `manage.py` from a `git worktree` at its exact commit using a copy of synthetic refunds data. The trusted launcher sets the session cookie before Django starts; execution provenance is the candidate commit plus this launcher version. Candidate processes receive an explicit environment-variable allowlist and have no controller DB, Devin key or merge credential. **Worktree/process separation is not a security sandbox**: candidate Python can still inspect the local host. Only trusted demo source should be executed locally. Containers, resource/egress limits, secrets isolation and a trusted remote runner are enterprise follow-up work.

`control.policy` independently diffs the actual Git tree against the recorded base; a well-formed copy-only `refunds/copy.json` patch with unchanged keys and string values is the only auto route. Templates always autoescape those strings. All frontend/behavior changes require tools-admin approval of the checked head/base. Refund amounts, decisions, auth, migrations, dependencies, controller, CI and policy require a separate refund-policy owner attestation plus tools-admin approval. The controller's check script is not loaded from candidate source. The separate `.runs/release-tree` worktree begins at the pinned demo baseline and advances via serialized local merges while the controller's tracked source remains current. Pending feedback, failed/stale checks, a changed base and local conflicts block merge. Release is distinct: the supervisor swaps to the merged checkout, health and authenticated browser smoke run, and on failure the previous revision is selected again. Data is shared only between successive runtime versions (not previews), so schema changes are intentionally not part of these demo patches.

The named `vulnerable-null-note-v1` baseline uses `note.trim()` in `refunds/static/refunds/detail.js`. `RF-LEGACY-NULL` is created only by the tools-admin demo control and retains a real `NULL` note. The browser throws, and the global handler posts an actual stack with a correlation ID. The local fix fixture uses `(note ?? "").trim()`, preserving the record and telemetry, then the trusted Playwright check requires correct text on that same case. It must fail if pointed at the baseline.

Official Devin v3 endpoints verified against [API overview](https://docs.devin.ai/api-reference/overview), [create session](https://docs.devin.ai/api-reference/v3/sessions/post-organizations-sessions), [get session](https://docs.devin.ai/api-reference/v3/sessions/get-organizations-session), [list messages](https://docs.devin.ai/api-reference/v3/sessions/get-organizations-session-messages), [send message](https://docs.devin.ai/api-reference/v3/sessions/post-organizations-sessions-messages), [GitHub integration](https://docs.devin.ai/integrations/gh), [security profiles](https://docs.devin.ai/product-guides/security-profiles). Organization URLs use `/v3/organizations/{org_id}/sessions` and `/sessions/{devin_id}/messages`, bearer `cog_` service credentials, `org-`/`devin-` identifiers, create `{prompt,title,repos,resumable,tags}`, response `session_id/url/status`, message pages `{items,end_cursor,has_next_page}` and send `{message}`. Creating requires `UseDevinSessions`, sending requires `ManageOrgSessions`, viewing needs creator/session grant or `ViewOrgSessions` for other sessions. Account-specific grants, integration/repository connectivity, security profiles and actual usage cost cannot be verified without provided access. API request failures never include secret-bearing response bodies. Creation with ambiguous response is blocked pending session reconciliation, not blindly retried; ambiguous feedback must be verified against actual session messages. A local `git ls-remote` advertised ref check alone cannot prove Devin's GitHub integration permissions: this must be validated with the account owner.

The browser/UI, refund approval concurrency and locally authored fixture commits are exercised locally. No part has been exercised with a real Devin session, remote repository, GitHub PR/merge protection or production payments. The deterministic local pretriage catches obvious missing context/duplicates/sensitivity; live mode additionally asks Devin for triage in the creation prompt, but does not trust agent advice as policy. Duplicate detection is exact normalized text, not semantic similarity. Server-side sanitization strips common credential patterns from captured stacks but is not a general DLP system. Demo passwords, local host execution, naive vulnerability injection and limited telemetry retention are not enterprise controls.

Follow-up work: configure scoped repo permissions and protected remote reviews; build containerized candidate isolation/egress; SSO and access reviews, CSRF/CSP/security hardening, retention/DLP, calibrated semantic triage, enterprise audit backups, real provider contract tests, and deployment health/rollback infrastructure. Independently log eval failures as regression checks, then rerun fresh trials after changing triage/change/feedback prompt version or agent configuration. Record actual source revisions and available usage instead of attributing replay to Devin.
